# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`@jorgegb/harness-init` is an npm CLI (`npx @jorgegb/harness-init`). It scaffolds an "AI dev harness" into a target project: `AGENTS.md`, `init.sh`, `feature_list.json`, `progress/`, `docs/`, `specs/`, opencode agent definitions (leader, spec-author, implementer, reviewer, plus optional extras), and `opencode.jsonc`.

The repo is also **dogfooded**: the root-level `AGENTS.md`, `CHECKPOINTS.md`, `init.sh`, `feature_list.json`, `progress/`, `docs/`, `.opencode/agent/` and `opencode.jsonc` were generated by this tool (with a Linear task backend). They describe the SDD/TDD workflow that agents are expected to follow here, so read `AGENTS.md` for the workflow rules. Don't confuse these generated files with the source templates in `templates/`. To change what users get, edit `templates/`, not the root copies.

## Commands

The project uses pnpm (CI and `init.sh` both rely on it) and requires Node >= 20.

```sh
pnpm install
pnpm dev -- [flags]          # run the CLI from source via tsx (e.g. pnpm dev -- --yes --stack python)
pnpm build                   # tsc -> dist/ (bin entry is dist/cli.js)
pnpm typecheck               # tsc --noEmit (also aliased as `pnpm lint`; there is no separate linter)
pnpm test                    # vitest run
pnpm vitest run tests/unit/plan.test.ts      # single file
pnpm vitest run -t "rejects project name"    # single test by name
./init.sh                    # harness verification: env, base files, feature_list.json/specs consistency, tests
```

CI (`.github/workflows/ci.yml`) runs `pnpm typecheck` and `pnpm test` on Node 22, plus an OSV scan of `pnpm-lock.yaml`. Releases use Changesets: add a changeset (`pnpm changeset`) for user-facing changes. On `main`, `release.yml` opens a version PR or publishes to npm.

## Architecture

The pipeline goes **detect → answers → plan → apply**, and each stage has its own module in `src/`:

- `cli.ts` is the entry point. It handles `--help`/`--version`, refuses to run as root unless `--allow-root` is passed, and builds an `Answers` object. With `--yes` it uses defaults merged with parsed flags. Otherwise it runs the `@clack/prompts` wizard. It then calls `buildPlan` and `applyPlan` and handles overwrite conflicts interactively.
- `detect.ts` works only from marker files. It returns the stack (python/node/go/rust/generic), the framework (react/astro/next/fastapi/django/flask/none), the CLI (opencode/claude) and the project name.
- `prompts.ts` contains the interactive wizard (`promptWizard`) and the flag parser (`parseArgs`).
- `plan.ts` holds the core logic. `buildRenderVars(answers)` computes every `{{VAR}}` substitution. Task-backend-specific text (json/linear/notion) lives here as `Record<TaskBackend, string>` maps, along with each agent's description and mode (`ALL_AGENT_META`). `buildPlan` returns a list of `FileAction { path, content, exists: create|overwrite|skip, mode: normal|append }`. Which files are included depends on the answers (sdd, tdd, bestPractices, learningMode, seedDemo, agents, taskBackend, cli). `.gitignore` is merged line-by-line with any existing one. The opencode `AGENTS.md` addendum is an `append` action to the same path.
- `permissions.ts` defines every agent's opencode permissions in one place. Both the `opencode.jsonc` entries and each `.opencode/agent/*.md` frontmatter (`{{AGENT_PERMISSION}}`) are generated from it. opencode applies the **last** matching rule, so broad rules come first and exceptions after. Change permissions here, never in the agent templates.
- `approve.ts` implements `harness-init approve <feature>`, which writes `specs/<feature>/APPROVED` with a spec hash. The same hash is recomputed in Python inside `templates/shared/init.spec-check.harness.sh`. The two must stay identical; `tests/unit/approve.test.ts` runs the real Python check against Node-written approvals to catch drift.
- `templates/opencode/plugins/harness-guard.js` is a plain-JS opencode plugin, copied verbatim. It enforces the approval gate inside opencode and holds a third copy of the spec hash. It must export only the plugin function, because opencode loads every export as a plugin. `tests/unit/harness-guard.test.ts` drives it through its hook interface with a fake client.
- `render.ts` contains `loadTemplate` and `render`. Rendering is a plain `replaceAll` of `{{KEY}}` with no escaping or conditionals, so any placeholder without a var stays in the output literally. `getStackVars` builds `STACK_CONVENTIONS`, `RUNTIME_CHECKS` and `TEST_COMMAND` by concatenating `templates/stack/<stack>/` with optional `templates/stack/<stack>/<framework>/` overrides. The per-stack and per-framework test commands are inline bash strings defined in this function.
- `apply.ts` writes files. It creates directories, `chmod 755`s any `*.sh` file, and collects written/appended/skipped/errors results.

Templates are resolved at runtime from `../templates` relative to the compiled module (`import.meta.dirname`). That's why `templates/` is shipped in the npm `files` list next to `dist/`.

Template layout:
- `templates/shared/` holds files generated for every target.
- `templates/opencode/` holds files specific to the opencode adapter.
- `templates/stack/<stack>[/<framework>]/` holds `init.checks.sh`, `conventions.md` and `.gitignore.txt`.

To add a new render var, add it in three places: the `RenderVars` interface (`render.ts`), the `buildRenderVars` return value (`plan.ts`), and the templates that use it. To add a new stack or framework, update the `Stack`/`Framework` types and detection (`detect.ts`), the label maps in `plan.ts`, the test-command maps in `render.ts`, and add a `templates/stack/...` directory.

`--cli` accepts `claude`/`codex`, but only the `opencode` adapter generates CLI-specific files today.

## Tests

- `tests/unit/` calls `buildPlan`/`applyPlan`/`detect`/`render` directly against temp dirs under `tests/tmp-*`.
- `tests/e2e/adversarial/` spawns the real CLI (`node --import tsx src/cli.ts`) to check path traversal, hostile names and similar input. It needs `node_modules/tsx` installed.
- `tests/lint/notion-safe.test.ts` scans every `.md`/`.tmpl` under `templates/` and fails on markup that breaks Notion rendering (`<details>`, `<summary>`, admonitions `!!!`/`:::`, capitalized JSX-like tags). Keep templates plain Markdown.

## Security constraints (from README / SECURITY.md)

The installer must stay fully offline, run no `postinstall` scripts, never write outside the target directory, and never overwrite silently. Conflicts get a prompt, are skipped under `--yes`, and are overwritten only with `--force`.
